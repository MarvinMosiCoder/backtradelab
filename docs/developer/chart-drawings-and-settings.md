# Chart Drawings and Settings

## Purpose

Users create chart annotations and save reusable tool defaults. Drawings are scoped to a user and market identity.

| Route/file | Responsibility |
|---|---|
| `GET/PUT /market-drawings` | Load/save drawing collection |
| `GET/PUT /market-tool-settings` | Load/save tool templates |
| `MarketDrawingController.php` | Drawing validation and ownership |
| `MarketToolSettingController.php` | Template validation and ownership |
| `MarketDrawing.php`, `MarketToolSetting.php` | Persistence |
| `ChartStage.jsx`, `ReplayPanel.jsx`, `utils.js` | Editing UI and geometry |

## Flow

1. Active exchange/category/symbol changes.
2. The chart requests that user's drawing record for the market.
3. Pointer actions create/select/move/resize drawing data.
4. Saves are serialized so an older request cannot overwrite newer state.
5. The server updates or creates the user-and-market record.
6. Tool templates load once per user and are saved independently of drawings. The persisted settings key remains `presets` for backward compatibility.

Browser mirrors use scoped keys such as `replay-drawings:{userId}:{exchange}:{category}:{symbol}`. They are recovery/cache aids, not authorization or the source of truth.

Drawings are market-scoped rather than timeframe-scoped. Loading drawings is independent from candle loading, a failed refresh retains the last local/server copy, and absolute drawing times are projected onto the active timeframe. Price Range uses a rectangular two-axis shape with corner and edge handles. Long/short Entry, TP, and SL values render in a dedicated right-axis label layer and remain visible whether or not the drawing is hovered or selected.

Price Range also renders a vertical directional arrow centered in the box (`ChartStage.jsx`, in the same `'rect'`/`'price-range'`/`'date-range'`/`'price-date-range'` box-render block, gated to `d.type === 'price-range'` only): green pointing up when `end.price > start.price`, red pointing down when lower, hidden while flat (`end.price === start.price`) or during the live drag preview (`temp-` id). Direction is based purely on the price delta, not which corner the user dragged from — reuses the existing `getArrowHeadPoints` helper already used for the `forecast`/`arrow` tool types rather than a new arrowhead implementation. Date Range and Price & Date Range do not get this arrow (a duration/bar-count range has no up/down direction to show).

## Maintenance

- Add a new tool in constants/tool menus, creation state, rendering, hit testing, movement, resizing, serialization, and validation.
- Preserve unknown/new drawing fields during compatible updates where appropriate.
- Keep SVG overlay boundaries aligned with the main price pane.
- Never query drawings or settings without `adm_user_id`.

## Verification

- Every drawing type create/select/move/resize/delete.
- Reload and market switching.
- Create on 5m, switch to 1h and back to 5m, and confirm geometry and selection remain available.
- Resize Price Range independently from every edge and corner.
- Price Range arrow points up (green) when the box's end price is higher than its start price, down (red) when lower, regardless of which corner was dragged first; no arrow when the two prices are equal.
- Confirm long/short Entry, TP, and SL axis labels remain visible before, during, and after hover/selection.
- Hover each long/short profit or stop zone and confirm the centered Target/Stop and Open P&L details appear, then disappear on pointer leave when the drawing is not selected.
- Select a long/short drawing and confirm its detail labels remain visible after pointer leave. Target and Stop must each stay centered on one line; Open P&L and Risk/Reward remain a two-line badge.
- Two users in one browser remain isolated.
- Rapid saves preserve the latest state.
- Indicator panes do not receive drawing overlays.

Related: [Trading chart](trading-chart.md), [Replay](replay-and-progress.md).
# Ready tools and expanded drawing set

Each left-rail drawing category has a ready-tool button and a separate list trigger. Choosing a tool updates that category's ready icon and saves `readyTools` through `/market-tool-settings`, with the existing per-user local fallback. The ready button activates the saved tool immediately.

The chart supports lines, rays, extended lines, arrows, horizontal/vertical lines, paths, Fibonacci tools, parallel channels, position/forecast tools, rectangles, circles, annotations, and Price Range, Date Range, and Price & Date Range. Range labels show price/percentage movement, duration, and candle count as applicable. Saving a template over an existing case-insensitive name requires confirmation.

**Circle** (`'circle'`) is a `BOX_TOOL_TYPES` member, not a new interaction pattern — it reuses the rectangle tool's two-point bounding-box math verbatim (creation, drag-move, 8-point resize handles, hit testing all key off `BOX_TOOL_TYPES.includes(type)`, which doesn't care what shape gets drawn inside the box) and only diverges at the final render step in `ChartStage.jsx`, where `d.type === 'circle'` draws an `<ellipse>` inscribed in the box instead of a `<rect>`. `BOX_TOOL_TYPES` is unfortunately duplicated as a separate module-level constant in both `TradingViewChart.jsx` and `ChartStage.jsx` (not shared from `utils.js`), plus a third inline literal array at the box-rendering `if` check in `ChartStage.jsx` — all three needed the same addition and must stay in sync for any future box-style tool too.

**Extended Line** (`'extended-line'`) is a line-like tool (`isLineLikeDrawing`) that extends infinitely in both directions, unlike `ray` (extends one direction only). It follows `ray`'s established pattern exactly rather than `vertical-line`'s: the real click anchors stay at `screen.p1`/`screen.p2` (so resize handles and drag-to-move operate on the actual points the user placed, via the generic `isTwoPointDrawing` path), and two *additional* screen-only fields, `rayStart`/`rayEnd`, hold the edge-of-viewport extension for rendering and hit-testing only — computed from the same point-slope line equation as `ray`, just applied to both ends instead of one. Every place that reads `d.screen.rayEnd ?? d.screen.p2` to find the line's visible endpoint has a symmetric `d.screen.rayStart ?? d.screen.p1` counterpart for the visible start (`ChartStage.jsx`'s line renderer and label-gap calculation, `hitTestDrawing`'s click detection). `getLineLabelPosition` was deliberately left reading the real `p1` (not `rayStart`) for a centered label's anchor — the label sits nearer the drawn segment instead of drifting to the chart edge, a readability choice, not an oversight.

If another "extends beyond its two points" tool is ever added, extend from `extended-line`'s `rayStart`/`rayEnd` pattern (additive screen fields, real anchors preserved) rather than `vertical-line`'s (which overwrites `screen.p1`/`p2` outright and works only because a vertical line's real anchor point is meaningless once it's forced to span full height — that shortcut doesn't generalize to a tool where the anchors still matter for dragging).

The chart context menu's **Clear Tools** action clears drawings through the same confirmation, persistence, and undo path as the drawing rail. It is disabled when no drawings exist and does not remove indicators, alerts, positions, or templates.

Selecting the toolbar settings action opens a staged drawing editor with Style, Text, Coordinates, and Visibility tabs. **Ok** persists the edited drawing while **Cancel** discards the draft. Coordinate fields update supported point-based drawings, visibility can be limited to the active timeframe, and locked drawings remain selectable but cannot be moved or resized.

The dialog's footer also has a **Template** dropdown (left of Cancel/Ok), matching TradingView's pattern: **Save as...** opens a second, focused modal (just a name field, Cancel/Save) that reuses the exact same save path as the older Templates rail flyout — `onSaveSelectedToolPreset`/`handleSaveSelectedToolPreset` in `TradingViewChart.jsx` — including its case-insensitive duplicate-name overwrite confirmation (`window.confirm`, matching the flyout's existing behavior rather than introducing a second, differently-worded one). **Apply defaults** resets the in-progress draft (color to `DRAWING_COLORS[0]`, width 1, solid line, non-bold/non-italic 12px text, top/center label alignment) without closing the dialog or touching any saved preset — it's a local `setDraft` call inside `DrawingSettingsDialog`, so Cancel still discards it and only Ok commits it. This is a second entry point onto the *same* preset system the Templates rail flyout already exposes (`presetItems`, `canUsePresets` computed once in the outer `ReplayPanel` component and passed down) — it does not duplicate storage or add a new persistence path.

The Text tab's Size select (`TEXT_SIZES` in `constants.js`, 10–32px) sets `drawing.textSize`, read by `ChartStage.jsx` wherever a drawing's text renders: the standalone `text` tool's floating `<span>` and every `labelText` badge on lines/paths/boxes (all default to 12px when unset, so existing saved drawings render unchanged). This field follows `textBold`/`textItalic`'s exact plumbing, but that plumbing has a non-obvious extra hop worth knowing before adding a fourth text-style field: the settings dialog's "Ok" button (`DrawingSettingsDialog`'s `onApply` in `ReplayPanel.jsx`) does **not** forward the whole draft — it re-lists specific fields into the object it hands to `onDrawingLabelChange`. A field only reaches the drawing (and, for the `text` tool type, `handleDrawingLabelChange`'s own separate persisted-preset whitelist in `TradingViewChart.jsx`) if it's named in *both* places; adding it to the tab's UI alone silently does nothing on Ok.

Long/short position drawings use an exchange-style risk/reward layout with distinct profit and stop zones and draggable entry, target, and stop handles. The zones have no outer, top, or bottom border; a thin entry divider separates them. TP/Entry/SL price-axis badges are always visible. Hovering anywhere inside either zone, or selecting the drawing, reveals the detailed labels: centered single-line Target and Stop badges plus a centered two-line Open P&L and Risk/Reward badge. Pointer leave hides those details only when the drawing is not selected. Long targets/stops are constrained above/below entry respectively; short drawings use the inverse ordering, including while creating or resizing the tool.

# Shapes (Triangle, Arc, Curve, Double Curve), text-marker family, lock-all, and Show/Hide

Four new shapes joined the Geometric Shape group and ten text-marker types joined Annotation, all reusing existing interaction machinery rather than inventing new ones:

- **Triangle, Curve, Double Curve** are 3-point tools (`THREE_POINT_SHAPE_TYPES` in `TradingViewChart.jsx` / `THREE_POINT_TYPES` in `ChartStage.jsx` — two names for an overlapping-but-not-identical concept, see below) added to the *same* `['fib-extension', 'parallel-channel']` special-case list that already collects a third `anchor` point on a 3rd click, at all four call sites (temp-drawing creation, mousemove preview, finalize-on-click, and the resize-handle generator) — search for `THREE_POINT_SHAPE_TYPES`/`THREE_POINT_TYPES` if adding a fifth. They're also added to `isLineLikeDrawing`, which means the generic `resized[handle] = coords` line already used for `fib-extension`'s anchor handle drag "just worked" for these too with no new resize code. Rendering intercepts `SHAPE_TOOL_TYPES` right after the `isFibonacciDrawing` branch (before the generic straight-line fallback) in `ChartStage.jsx`: triangle draws a `<polygon>` from p1/p2/p3, Curve draws a quadratic `<path>` (`Q p3`) using p3 as the control point, Double Curve derives two cubic control points by offsetting the p1–p2 midpoint by however far p3 sits from *that* midpoint (a hand-rolled S-curve approximation, not a real second anchor point — good enough to look visually distinct from Curve, not claiming more fidelity than that). Until the 3rd point exists (`d.screen.p3` unset), all three fall through to the plain two-point line preview, matching `parallel-channel`'s existing UX during creation.
- **Arc** is a plain 2-point tool (no anchor) rendered as a fixed-curvature SVG arc (`radius = distance(p1,p2) * 0.75`) — a simplification, not TradingView's real dynamically-adjustable arc. Hit-testing for all four shapes approximates against straight edges (p1–p2, plus p1–p3/p2–p3 for the 3-point ones) rather than the actual curve/arc geometry; clicking exactly on a pronounced bulge, away from those chords, may not select it. Good enough for now; revisit if it's reported as an actual usability problem.
- **Text-marker family** (`TEXT_MARKER_TYPES`, duplicated as a module constant in `TradingViewChart.jsx`, `ChartStage.jsx`, and `ReplayPanel.jsx` — same duplication pattern as `BOX_TOOL_TYPES`, all three must stay in sync): Anchored Text, Note, Anchored Note, Callout, Comment, Price Label, Price Note, Signpost, Flag Mark. All ten (including the original `text`) share one data shape (`point`, `text`, `color`, `textBold`, `textItalic`, `textSize`) and one creation flow (click → `TextInputPopover` → save) — every place that used to hardcode `drawing.type === 'text'` now checks `TEXT_MARKER_TYPES.includes(drawing.type)` instead (there were **13 such call sites** across the two files: settings/preset persistence, hit-testing, drag-anchor detection, `getDrawingTimes`, screen-coordinate computation, resize-handle exclusion, and both of `ReplayPanel.jsx`'s "what's the current drawing's display name" helpers). They're visually differentiated only by an icon in front of the text (`TEXT_MARKER_ICONS` in `ChartStage.jsx`) plus two special cases: **Signpost** gets an auto-incrementing number badge instead of an icon (`drawing.signpostNumber`, computed once at creation time as `count of existing signposts + 1`, never renumbered afterward even if earlier signposts are deleted) and **Callout** gets a bordered speech-bubble background. **Price Label**/**Price Note** additionally draw a dashed line from the marker to the right chart edge at the same Y (`PRICE_ANCHORED_MARKER_TYPES`, `d.screen.pRight`) to *suggest* price-axis anchoring, but they are not actually price-only anchored — dragging still moves them in time too, same as every other marker. This is a deliberately shallow set of variants (one interaction, one renderer, cosmetic differentiation) rather than bespoke widgets — do not assume Callout has real pointer-line geometry or Signpost renumbers on delete; check the code before relying on either.
- **Group icons**: `TOOL_GROUPS` entries gained a `groupIcon` field (`Spline`, `Sigma`, `Compass`, `Shapes`, `MessageSquare`), shown in the compact rail's `<details>` summary and the per-group flyout title in `ReplayPanel.jsx`. This is independent of each group's rail *button* icon, which intentionally still shows the last-used ("ready") tool in that group, not the group icon — don't conflate the two.
- **Lock all drawings** (rail button, `Lock`/`Unlock` icon) is a session-only override, not a bulk edit — `allDrawingsLocked` (state + `allDrawingsLockedRef` for the mouse handlers) is OR'd alongside each drawing's own `locked` flag at both places that gate drag/resize start. It never touches individual drawings' `locked` values, so turning it off doesn't reveal which ones were already locked before you turned it on — nothing to reconcile either way.
- **Show/Hide** (rail button, `Eye`/`EyeOff` icon) is `hiddenLayers: { drawings, indicators, positions }` in `TradingViewChart.jsx`, also session-only (not persisted, not synced to the server). "Hide drawings" and "Hide positions" filter `renderedDrawings` at the source (`isPositionDrawing` splits the two categories), so hidden items are also un-hit-testable — you can't select or drag something invisible. "Hide indicators" is ANDed into the existing per-indicator visibility effect (volume/SMA/EMA/RSI/MACD), so it composes with each indicator's own on/off state rather than overriding it permanently. "Hide all" is a single toggle: hides all three if any are visible, shows all three only when all three are already hidden. Scope note: "positions and orders" only covers `long-position`/`short-position` *drawings* — it does not touch live backtest order/position overlays rendered from `backtestAccount` state, which is a separate rendering path this didn't touch.

**Found and fixed two pre-existing bugs while wiring the above, unrelated to what was asked but directly adjacent to the code being touched:**
1. `parallel-channel`'s filled-two-line-channel rendering was dead code — it lived inside `if (isPathDrawing(d))`, but `d.type === 'parallel-channel'` can never be true there (`isPathDrawing` requires `type === 'path'`), so a parallel-channel drawing always silently fell through to the generic single-line renderer and never showed as an actual channel. Moved to the correct spot (alongside the new shape branches, inside `isLineLikeDrawing`, after the fibonacci branch) — it now renders as originally intended.
2. Its "drag the anchor" resize-handle *dot* also never appeared (a separate, visual-only handle list in `ChartStage.jsx` only checked `selectedDrawing.type === 'fib-extension'`, not `'parallel-channel'`, even though the actual anchor drag has always worked via the other, correct handle list in `TradingViewChart.jsx`) — the dot just never rendered. Both bugs were shipped together, likely from copy-pasting fib-extension's special case without extending it to its sibling. Fixed alongside adding the same handle for the three new 3-point shapes.

The settings modal's "Ok" whitelist (`onApply` in `ReplayPanel.jsx`, see the Template/Text-size note above) had a *third* undiscovered `nextDrawing.type === 'text'` check gating whether an edited marker's `text` field actually reached the drawing — found and fixed during this pass, since it would otherwise have silently no-op'd editing any of the nine new marker types' content via the settings modal (only the original `text` type would have worked). Anywhere this codebase says `=== 'text'`, check whether it should really say `TEXT_MARKER_TYPES.includes(...)` now.
